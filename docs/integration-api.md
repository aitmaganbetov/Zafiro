# Интеграционный API Zafiro (v1)

Документ для разработчиков и администраторов Zafiro: как устроен API для внешних систем клуба,
какие у него гарантии безопасности, как его эксплуатировать и что показали проверки.
Справочник для интеграторов — `/docs/api` (Swagger UI по `resources/api/openapi-v1.yaml`).

## 1. Аудит существующих API (до v1)

Существующие маршруты `routes/api.php` **не изменены**: v1 живёт под отдельным префиксом `/api/v1`,
со своей аутентификацией и своим форматом ошибок. Тест `existing API endpoints keep their behaviour`
и все прежние тесты (`ApiAuthTest`, `ComputerAgentApiTest`, `ComputerHeartbeatTest`, `SettingsTest`)
проходят без изменений.

| Маршрут | Защита | Замечания |
|---|---|---|
| `POST /api/clubs/resolve` | throttle 10/мин, поиск по префиксу ключа установки + `hash_equals` | без замечаний |
| `POST /api/auth/login` | throttle 5/мин, неудачные входы в журнале | Sanctum-токен на 30 дней с ability `club:N`. Это путь для мобильных приложений и агента ПК — ключи API в приложения не встраиваются |
| `GET /api/auth/me`, `POST /api/auth/logout` | sanctum + current-club (+ subscription) | без замечаний |
| `POST /api/club-computers/*` | sanctum + current-club + subscription + throttle + policy | без замечаний |
| `GET /api/products` | sanctum + current-club + subscription + throttle 60/мин | доступно **любой** роли клуба, без пагинации. Контракт сохранён; для внешних систем — `/api/v1/products` с правом и курсором |
| `GET /api/settings/{section}/{key}` | то же | доступно любой роли клуба |

Как выбирается клуб: `SetCurrentClub` принимает `X-Club-Id` только среди клубов пользователя и
отклоняет заголовок, если токен привязан к другому клубу. Журнала API-запросов не было.

Рекомендации для старых маршрутов (не применялись: это изменение контракта, нужен план миграции
клиентов):
- ограничить `/api/products` и `/api/settings/*` ролями;
- добавить пагинацию в `/api/products`.

## 2. Архитектура

```
Внешняя система ── Bearer zfk_… ──▶ /api/v1/*
  LogApiRequest        журнал каждого вызова (и отклонённого): время, IP, префикс ключа, метод, путь, статус, мс
  LimitApiRequestSize  тело ≤ 256 КБ → иначе 413
  AuthenticateApiKey   ключ → клуб (CurrentClub), IP allowlist, запрет подмены клуба, блок перебора по IP,
                       запрет маршрутов без объявленного scope
  ApiRateLimit         атомарные счётчики: ключ (по умолчанию 120/мин) и клуб (600/мин)
  RequireApiScope      api.scope:products:read … (по умолчанию всё запрещено)
  ApiIdempotency       Idempotency-Key для записи (обязателен для склада и питания ПК)
  SubstituteBindings   {product}, {computer} ищутся только в клубе ключа → чужие id дают 404
  Контроллеры v1       переиспользуют действия веб-интерфейса (CreateProductAction, AdjustStockAction, …)
```

Порядок middleware закреплён в `bootstrap/app.php` (`prependToPriorityList`): ключ и клуб
определяются раньше rate limit и привязки моделей.

### Ключи API (`app/Services/Integrations/ApiKeyManager.php`)
- Формат `zfk_<8 символов префикса>_<40 символов секрета>`. В БД хранится только
  `sha256(ключ)` (`api_keys.key_hash`). Секрет показывается один раз: в ответе на создание
  или перевыпуск, со страницей `Cache-Control: no-store`. В сессию он не попадает.
- Проверка: префикс ищется по уникальному индексу, затем хеш сравнивается через `hash_equals`.
  Полный список ключей не загружается никогда.
- Метаданные проверенного ключа кэшируются на 5 минут по префиксу: клуб, права, IP, лимит, срок,
  статус владельца и подписки. Секрета в кэше нет. Кэш сбрасывается сразу при:
  - отзыве и перевыпуске ключа;
  - изменении роли или права `can_manage_integrations` у создателя ключа и при удалении его членства;
  - изменении подписки;
  - изменении названия, языка или настроек клуба.

  Неизвестные префиксы кэшируются отрицательно на 60 секунд.
- Ключ перестаёт работать, когда:
  - его отозвали;
  - истёк срок;
  - у создателя больше нет права управлять интеграциями;
  - подписка клуба неактивна (ответ 402).
- Изменения через API записываются в журнал действий от имени создателя ключа, с IP запроса и
  `details.api_key = <префикс>`.

### Изоляция тенантов
- Клуб берётся только из ключа. Если `club_id` в query или body либо `X-Club-Id` указывает на
  другой клуб, ответ — `403 tenant_override_forbidden`. Контроллеры клуб из запроса не читают.
- Все выборки идут через глобальный scope `BelongsToClub`. Привязка моделей выполняется после
  установки клуба. Правила `exists`/`unique` явно ограничены `club_id`.
- Чужие id в пути дают 404 (как несуществующие), чужие id в теле — 422.
- Задачи очереди (вебхуки) не зависят от текущего клуба: читают записи по id без scope.

### Права (scopes) — `config/integrations.php`
`products:read`, `products:write`, `stock:write`, `sales:read`, `computers:read`, `bookings:write`,
`computers:control` (опасное), `tariffs:read`, `members:read` (опасное, персональные данные).
Для «бронирований» используется бронь ПК (`is_reserved`): отдельной сущности брони в Zafiro нет.
Опасные операции дополнительно ограничены:
- `computers/control`: обязателен Idempotency-Key, не более 50 ПК за вызов, перезагрузку и
  выключение нельзя применить к ПК с активной сессией клиента (409); команда доходит до агента
  со следующим heartbeat (`ComputerPower`), включение — Wake-on-LAN от включённых ПК клуба;
- `stock-movements`: обязателен Idempotency-Key, списание сверх остатка запрещено;
- в `members` телефоны маскируются, e-mail не отдаётся.

### Вебхуки
- `WebhookDispatcher` создаёт `webhook_deliveries` внутри бизнес-транзакции и ставит задачу
  `DeliverWebhook` после commit: откат операции = ничего не отправлено.
- Подпись: `X-Zafiro-Signature: v1=hex(HMAC-SHA256(secret, "{timestamp}.{body}"))`.
  Также передаются `X-Zafiro-Timestamp` и `X-Zafiro-Delivery` (uuid). Пример проверки — в `/docs/api`.
- Секрет вебхука хранится зашифрованным (`encrypted` cast): он нужен Zafiro для подписи, поэтому
  хеша недостаточно. Показывается один раз.
- Защита от SSRF (`WebhookUrlGuard`):
  - только https (в проде) и порты 80/443/8080/8443;
  - без логина и пароля в URL;
  - все адреса хоста должны быть публичными;
  - запрос привязан к проверенному IP (`CURLOPT_RESOLVE`), поэтому DNS rebinding не сработает;
  - редиректы запрещены, таймаут 5 секунд.
- Повторы через 10 с, 1 мин, 5 мин, 30 мин и 2 ч. После 20 неудачных доставок подряд endpoint выключается.
- События и места отправки:
  - `product.created` — `CreateProductAction`;
  - `product.updated` — `UpdateProductAction`;
  - `stock.changed` — `AdjustStockAction`, `CreateProductAction` и `CashRegisterService::sale`;
  - `sale.completed` — `CashRegisterService::sale`;
  - `computer.reservation_changed` и `computer.controlled` — web `ClubComputerController::control` и API.

### Интерфейс: «Настройки → API и интеграции» (`/settings/integrations`)
- Доступ — владелец и сотрудники с правом `club_memberships.can_manage_integrations`
  (Gate `manage-integrations`). Выдаёт и снимает право только владелец.
- Ключи: создание с правами, IP или подсетями, лимитом и сроком; перевыпуск и отзыв;
  последнее использование (время, IP).
- Вебхуки: создание, включение и выключение, новый секрет, удаление; последние доставки с
  кнопкой «Повторить».
- Последние 30 запросов к API клуба.
- Все действия записываются в журнал действий:
  - `api_key.created`, `api_key.rotated`, `api_key.revoked`;
  - `webhook.*`;
  - `integrations.permission_changed`.

## 3. Данные (миграция `2026_10_13_190912_create_integration_api_tables`, только добавление)
- `club_memberships.can_manage_integrations`
- `api_keys`: unique `prefix`, индекс `(club_id, revoked_at)`
- `api_request_logs`: индексы `(club_id, created_at)`, `(api_key_id, created_at)`, `created_at`
- `api_idempotency_keys`: unique `(api_key_id, idempotency_key)`
- `webhook_endpoints`, `webhook_deliveries` (unique `event_id`)

Списки v1 используют курсорную пагинацию по `id` внутри клуба. Её обслуживают существующие
индексы `(club_id, id)` и `club_id`, поэтому глубина страницы на стоимость не влияет.

## 4. Эксплуатация
- **Cron (обязательно для вебхуков и очистки):**
  `* * * * * cd /home/admzafiro/Zafiro && php artisan schedule:run >> /dev/null 2>&1`
  - Каждую минуту запускается `queue:work --stop-when-empty --max-time=50` (демон не нужен).
  - Каждый час — `integrations:prune`. Он удаляет:
    - журнал API старше 90 дней;
    - ключи идемпотентности старше 24 часов;
    - завершённые доставки старше 30 дней;
    - просроченные строки таблицы `cache`.
- **Переменные окружения (необязательные):**
  - `API_KEY_RATE_LIMIT` (120), `API_KEY_RATE_LIMIT_MAX` (1000), `API_CLUB_RATE_LIMIT` (600);
  - `WEBHOOK_REQUIRE_HTTPS` (true), `WEBHOOK_ALLOW_PRIVATE_HOSTS` (false).
- **Redis.** Сейчас кэш, rate limit и очередь работают на драйвере `database`. Переход:
  установить Redis и расширение phpredis (или predis), затем `CACHE_STORE=redis`,
  `QUEUE_CONNECTION=redis`. Код менять не нужно.
- **Выкладка:** `php artisan migrate`, `translations:sync`, `route:cache`, `npm run build`,
  плюс строка cron выше (однократно).

## 5. Проверки

Автотесты: `IntegrationApiAuthTest`, `IntegrationApiResourcesTest`, `WebhookTest`,
`IntegrationSettingsTest`. Покрыто:
- изоляция клубов на каждом списке;
- IDOR: чужие id в пути, теле и фильтрах;
- подмена клуба через заголовок, query и body;
- отозванные и истёкшие ключи, потеря прав создателем, неактивная подписка;
- матрица прав по всем 16 операциям, запрет маршрутов без scope;
- rate limit по ключу и по клубу, блокировка перебора по IP (отозванные ключи IP не блокируют);
- лимит размера тела;
- идемпотентность: повтор, другое тело, одновременный повтор;
- журнал без секретов и query string; в БД и кэше только хеш;
- 1 SQL-запрос на вызов при тёплом кэше (тестовый array-кэш), 1 индексированный запрос к
  `api_keys` при холодном;
- отсутствие N+1 в списках;
- вебхуки: подпись, изоляция, откат транзакции, повторы и отключение, SSRF (6 вариантов);
- страница настроек: права доступа, показ секрета один раз, валидация, чужие ключи и вебхуки;
- соответствие OpenAPI-спецификации маршрутам.

Нагрузочный прогон 13.10.2026. Условия:
- `php -S` с 8 воркерами и OPcache;
- MySQL 8.4 на этом сервере, во временной базе, удалённой после прогона;
- `CACHE_STORE=database`;
- 2 клуба по 300 товаров и 40 ПК.

| Сценарий | Результат |
|---|---|
| `GET /me`, 150 запросов, 8 параллельно | p50 18 мс, p95 31 мс, ~377 запросов/с |
| `GET /products?limit=50` | p50 21 мс, p95 37 мс, ~354 запросов/с |
| `GET /computers?limit=40` | p50 20 мс, p95 35 мс, ~353 запросов/с |
| 200 параллельных запросов двух клубов | 0 ответов с чужими данными |
| 40 вызовов отозванным ключом | все 401 |
| 60 параллельных вызовов при лимите 30/мин | ровно 30 × 200, 30 × 429 (до исправления пропускалось 34) |
| 20 параллельных списаний по 1 шт. при остатке 10 | 10 × 201, 10 × 422, остаток 0, балансы 9…0 без пропусков |
| 20 параллельных повторов с одним Idempotency-Key | 1 движение склада, ответы — 201 или 409, остаток +5 один раз |
| 40 обращений к id другого клуба | все 404 |
| Подмена клуба (заголовок, query, body) | все 403 |
| 30 неверных ключей с одного IP | 20 × 401, затем 429 (IP блокируется на минуту) |

- Все 918 вызовов прогона попали в `api_request_logs`.
- В дампе базы после прогона не найден ни один из 8 секретов.
- SQL-операторов на авторизованный вызов: 10. Из них 2 — бизнес-запрос и строка журнала,
  остальные — таблица `cache` (метаданные ключа, счётчики лимита, язык). С Redis они уйдут из MySQL.
- Цифры получены на встроенном сервере PHP. С php-fpm в проде абсолютные значения будут другими.
  Сравнивать стоит порядок величин и корректность под конкуренцией.

## 6. Как добавить операцию в v1
1. Добавить маршрут в `routes/api_v1.php` с `api.scope:<право>`. Без него тест упадёт, а
   маршрут будет отклонять все ключи. Если нужно новое право — добавить его в `config/integrations.php`.
2. Не читать `club_id` из запроса; модели — только с `BelongsToClub`; правила `exists`/`unique`
   ограничивать `club_id`.
3. Запись — через существующие действия или сервисы (журнал, блокировки), с `api.idempotent`.
4. Описать операцию в `resources/api/openapi-v1.yaml`: тест сверяет спецификацию с маршрутами.
5. Если операция меняет данные, о которых интеграциям нужно знать, — вызвать
   `WebhookDispatcher::dispatch()` внутри транзакции.
